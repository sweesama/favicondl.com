Blazor Favicon: guía práctica paso a paso

Si tu aplicación Blazor funciona pero su pestaña muestra el icono genérico de un documento, normalmente se debe a que falta un archivo estático o el enlace del head. Un Blazor favicon fiable necesita ambas cosas: un recurso servido por la aplicación y un enlace rel='icon' en el head del documento. El mismo enfoque funciona en los modelos de hosting habituales de Blazor.

Requisitos previos

Necesitas un proyecto de Blazor ya creado, su .NET SDK y un logotipo cuadrado. Si tu imagen de origen es PNG, usa Mzu favicondl para crear variantes SVG, ICO y PNG.

  • Blazor Web App: localiza el documento compartido en Components/App.razor.
  • Standalone WebAssembly: localiza el documento en wwwroot/index.html.
  • Hosted WebAssembly: identifica el index del cliente y el proyecto del servidor que lo publica.

1. Identifica la plantilla y su archivo head

Abre el archivo mencionado anteriormente y revisa su head. En una Blazor Web App, edita Components/App.razor; en WebAssembly independiente, edita wwwroot/index.html. En WebAssembly hospedado, edita el index del cliente, pero comprueba que el servidor desplegado sirva sus assets. Si una plantilla más antigua usa Pages/_Host.cshtml, edita ese documento en su lugar. Mantén el icono global fuera de los componentes de página normales, ya que allí podría aplicarse solo a una ruta.

2. Prepara un conjunto pequeño de iconos

Crea una carpeta para cada variante:

wwwroot/
└── favicon/
    ├── favicon.svg
    ├── favicon.ico
    └── apple-touch-icon.png

Coloca estos archivos dentro de wwwroot para que se publiquen como static web assets. Recomendamos un SVG escalable, un ICO que contenga imágenes de 16, 32 y 48 px y un PNG opcional de 180×180 para los accesos táctiles. Usa una ilustración cuadrada con margen y elimina el texto pequeño: desaparece a 16 px. Convierte o empaqueta los archivos con Mzu favicondl.

3. Añade los enlaces del Blazor favicon al head del documento

Añade los enlaces globales dentro del mismo head que contiene la URL base y los enlaces a las hojas de estilos:

<head>
  <base href='/' />

  <link rel='icon' href='favicon/favicon.ico'
        sizes='16x16 32x32 48x48' />
  <link rel='icon' type='image/svg+xml'
        href='favicon/favicon.svg' />
  <link rel='apple-touch-icon' sizes='180x180'
        href='favicon/apple-touch-icon.png' />
</head>

Estas URL relativas siguen la ruta base de la aplicación en lugar de dar por supuesta la raíz del dominio. La definición de rel='icon' del HTML Standard especifica un icono almacenado en un recurso externo; type y sizes describen el archivo. Mantén el enlace al ICO como fallback y define un conjunto global único en lugar de repetirlo en cada componente.

4. Actualiza los proyectos WebAssembly

Para WebAssembly standalone, pega los mismos enlaces en el head de wwwroot/index.html. Para WebAssembly hosted, añádelos al archivo index del cliente, publica la solución y revisa la salida del servidor:

dotnet publish -c Release

Comprueba que el wwwroot publicado contenga la carpeta favicon. Si no, cópiala en el wwwroot del host o ajusta la publicación de archivos estáticos. El index del cliente puede funcionar aunque un icono siga devolviendo 404.

5. Comprueba cómo se sirven los archivos estáticos

Si la solicitud directa de un icono devuelve 404, revisa Program.cs en busca de app.UseStaticFiles() o de un mapeo existente de endpoints para archivos estáticos. Si no existe ninguno de los dos, inserta esto antes del enrutamiento y del registro de endpoints:

app.UseStaticFiles();

No reemplaces el pipeline ni dupliques la gestión existente de archivos estáticos. Cuando falta este paso, las páginas pueden renderizarse mientras /favicon/favicon.ico falla. WebAssembly standalone no necesita middleware de ASP.NET Core porque su salida publicada es un sitio estático.

6. Verifica el archivo y la pestaña del navegador

Ejecuta el proyecto con dotnet run, sustituye 5000 por el puerto que aparece en pantalla en los comandos siguientes y solicita directamente los dos archivos:

curl -I http://localhost:5000/favicon/favicon.ico
curl -I http://localhost:5000/favicon/favicon.svg

Cada respuesta debe devolver 200 y un tipo de contenido de imagen. Consulta el código fuente de la página y confirma que los elementos link están en el head. Si el HTML es correcto pero la pestaña sigue mostrando el icono anterior, abre una pestaña nueva o una ventana privada e inspecciona el panel Network. Una recarga forzada normal puede no reemplazar un icono que ya esté en caché.

Repite la comprobación en la URL desplegada. Que funcione en localhost no demuestra que producción utilice el mismo base path o sirva los mismos archivos.

Problemas habituales

  • 404 en el favicon: confirma que el archivo está en wwwroot/favicon, que la ruta relativa coincide y que los archivos estáticos están mapeados.
  • Funciona en local, pero falla en una subruta: evita una URL /favicon/... limitada a la raíz cuando la base URL de Blazor apunte a otro lugar; mantén los enlaces relativos como se muestra.
  • Iconos duplicados u obsoletos: elimina el enlace al favicon antiguo de la plantilla y abre una pestaña nueva. Consulta la guía de resolución de problemas del favicon en localhost para obtener una lista de comprobación específica.
  • Un formato no funciona: exporta un SVG válido y autocontenido y conserva un ICO de respaldo con varios tamaños. Los estilos o recursos externos pueden hacer que un SVG no sea fiable como favicon.

Conclusión

Ajusta el modelo de hosting al archivo head, coloca los recursos bajo wwwroot y declara URL globales relativas. Prueba los archivos directamente antes de depurar la pestaña. Para una configuración de servidor no estándar, consulta la referencia más amplia sobre la configuración del favicon en ASP.NET Core.
