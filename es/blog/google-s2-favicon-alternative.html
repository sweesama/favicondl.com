Alternativas al servicio de favicon S2 de Google

Un panel que enumera 2.000 dominios necesita un icono por fila. Si estás evaluando una alternativa al servicio de favicons de Google S2, primero decide si necesitas una vista previa rápida almacenada en caché o el icono más exacto que publica realmente el sitio. Google S2 es adecuado para la primera tarea; el descubrimiento directo, para la segunda.

Existe además una cuestión de visibilidad en buscadores. La documentación de Google Search citada explica los requisitos de elegibilidad de los favicons, no un contrato de soporte de S2. Publica tu propio icono en una URL estable y decláralo mediante un enlace icon. Google indica que un icono elegible debe ser cuadrado y tener al menos 8×8 píxeles, recomienda uno de más de 48×48 píxeles y puede tardar varios días o incluso semanas en volver a rastrearse; la elegibilidad no garantiza que se muestre. La documentación de favicons de Google recoge las reglas.

Los enlaces rel='icon' de HTML identifican recursos de iconos. La selección puede depender del type, el tamaño y el media, por lo que un crawler no debería quedarse sin más con la primera URL. La documentación de WHATWG sobre relaciones de enlace define esta relación.

Cuándo utilizar cada opción

Usa Google S2 para obtener vistas previas alojadas rápidamente

Usa S2 en dashboards internos, vistas previas de enlaces o paneles de administración cuando basta con una imagen reconociable procedente de la caché. Así, el procesamiento de solicitudes se mantiene simple y se evitan conversiones locales.

Trata la respuesta como un dato auxiliar, no como la representación autorizada de tu marca. Mantén un icono de respaldo para cuando no haya resultados, registra el tiempo de recuperación y evita depender de una única fuente cuando importe la frescura de los datos. S2 no hace que tu dominio sea elegible para el favicon de Google Search.

Usa el descubrimiento directo cuando importar la precisión y el control

Usa el descubrimiento directo para sitios que controles o para dominios conocidos. Analiza la página principal con un parser de HTML, recopila los candidatos de iconos y respeta los atributos type, size y media; después, prueba la ruta convencional /favicon.ico únicamente como fallback. Este enfoque puede conservar el SVG y te permite cachear localmente el recurso elegido.

from urllib.parse import urljoin

def icon_candidates(page_url, discovered_hrefs):
    candidates = [urljoin(page_url, href) for href in discovered_hrefs]
    candidates.append(urljoin(page_url, '/favicon.ico'))
    return list(dict.fromkeys(candidates))

Establece límites para las solicitudes, bloquea los destinos de redes privadas y valida el estado, el content type y la firma del archivo en lugar de confiar en la extensión. La lista de comprobación de la favicon API orientada a producción cubre estas medidas de seguridad.

Usa DuckDuckGo como fallback alojado secundario

Usa DuckDuckGo cuando resulte inconveniente obtener recursos de sitios arbitrarios de terceros o cuando el servidor de origen bloquee a tu crawler. Prioriza el descubrimiento directo cuando sea posible, ya que permite conocer las opciones declaradas por el sitio.

La respuesta alojada no garantiza que la versión sea completa, esté actualizada o sea vectorial. La disponibilidad y la frescura de la caché quedan fuera de tu control, así que trátala como una fuente que puedes sustituir. Para consultar el comportamiento del endpoint y una comparación más detallada de formatos, consulta DuckDuckGo favicon API vs alternatives.

Usa Mzu favicondl para la descarga y la conversión manual

Usa Mzu favicondl para extracciones puntuales, entregas de diseño o un flujo de trabajo pequeño basado en revisiones, donde alguien selecciona el candidato. Convertir el PNG, SVG o ICO elegido es sencillo, pero la búsqueda automatizada de alto volumen tiene otros requisitos.

Por ejemplo, un equipo puede exportar un SVG para navegadores modernos, un PNG o ICO de respaldo para una gama más amplia de clientes y un Apple touch icon para las pantallas de inicio. Esto favorece una selección deliberada frente a una caché proxy opaca.

Recomendación

Elige según el nivel de control que necesites y no mediante un ranking universal:

  1. Tu propio dominio: publica el icono en una URL estable, decláralo mediante un enlace de icono y evita cambios innecesarios. Esta es la opción relevante para la elegibilidad en Google Search.
  2. Un directorio de iconos de terceros: usa primero el descubrimiento directo para obtener el SVG o el recurso raster previsto por quien publica el sitio.
  3. Un fallback alojado: usa S2 para vistas previas parametrizadas por tamaño o DuckDuckGo para un fallback orientado a ICO. Ofrece soporte para ambos sin convertir ninguno en la opción principal.
  4. Un sistema sensible a la privacidad o sin conexión: omite los servicios de terceros y obtiene el icono desde el origen o mediante un flujo de trabajo local.

Almacena la caché por dominio canónico, guarda el tipo de recurso y la fecha de descarga, valida cada archivo y mantén un fallback neutral. Esos detalles importan más que el hostname que proporciona el icono.

Conclusión

La mejor alternativa al servicio de faviconos de Google, S2, depende de la tarea: S2 para velocidad, DuckDuckGo para otro fallback alojado, descubrimiento directo para precisión y control, y Mzu favicondl para la descarga y conversión manual. En producción, los recursos alojados por quien publica el sitio deberían ser la opción predeterminada; los servicios externos deben permanecer como fallbacks sustituibles. Para mejorar la visibilidad en Google Search, publica tu propio icono en lugar de convertirlo en un proxy.
