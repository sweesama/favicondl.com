Favicon API — Get Website Icon Candidates Without Guesswork

You’re building a partner directory that needs to get a website icon from any domain. A good favicon API gets website icon candidates, validates them, and returns one stable result—not simply whatever happens to sit at /favicon.ico.

What the favicon API does

Mzu favicondl provides a browser-side path to find a site’s icon and download or convert it. In an automated product, use that lookup as the resource-resolution stage rather than treating an image URL as trusted output.

A dependable service handles four jobs:

  • Resolve: normalize the input URL and find declared icon links.
  • Fetch: retrieve the candidate and follow the site’s redirects.
  • Validate: confirm that the response is an image you can serve.
  • Cache: return a stable URL while allowing updates when the source changes.

The root file remains a useful fallback, but it is not the whole answer. The HTML Standard lists icon as a link relation for an external resource representing the page, so we recommend checking declared links before falling back to /favicon.ico.

Getting started: retrieve one website icon

  1. Open Mzu favicondl and enter the site’s full HTTPS URL.
  2. Run the lookup, then review the icon candidates it found.
  3. Choose the source that matches your use: browser favicon, Apple Touch Icon, or manifest icon.
  4. Download the file, or convert it to ICO, PNG, or SVG as required.

Start with the site’s homepage when you need one identity for the whole domain. Use a page-specific URL only when distinct icons are intentional.

If nothing is returned, check that the page is publicly reachable and inspect its icon declarations. A missing result can mean blocked retrieval, a client-rendered page, or no usable icon—not that the domain has no brand asset.

How a favicon API gets a website icon

If the lookup must run inside your application, separate discovery from delivery. Mzu favicondl remains useful for checking real candidates and converting assets; your service can expose the result as JSON or image bytes.

The following Node.js resolver reads the page HTML, selects a link whose rel list contains icon, resolves its URL, and fetches the image. It uses Cheerio for HTML parsing.

import { load } from 'cheerio';

export async function getWebsiteIcon(inputUrl) {
  const pageUrl = new URL(inputUrl);
  const pageResponse = await fetch(pageUrl, {
    headers: { 'User-Agent': 'FaviconResolver/1.0' },
  });

  if (!pageResponse.ok) {
    throw new Error(`Page request failed: ${pageResponse.status}`);
  }

  const contentType = pageResponse.headers.get('content-type') || '';
  if (!contentType.includes('text/html')) {
    throw new Error('The target did not return HTML');
  }

  const $ = load(await pageResponse.text());
  const iconLink = $('link[rel~=icon]').first();
  const href = iconLink.attr('href');
  if (!href) return null;

  const finalPageUrl = new URL(pageResponse.url);
  const iconUrl = new URL(href, finalPageUrl);
  const iconResponse = await fetch(iconUrl);

  if (!iconResponse.ok) {
    throw new Error(`Icon request failed: ${iconResponse.status}`);
  }

  return {
    sourceUrl: iconUrl.href,
    finalUrl: iconResponse.url,
    contentType: iconResponse.headers.get('content-type') || '',
    bytes: Buffer.from(await iconResponse.arrayBuffer()),
  };
}

This compact example is intentionally incomplete. Before accepting arbitrary URLs from the public, block requests to private and link-local addresses, cap redirects and response size, and set a timeout. Those controls help prevent server-side request forgery (SSRF) and oversized downloads.

Validate before returning the asset

  • Allow only http and https URLs.
  • Resolve relative links against the final redirected page URL.
  • Check both the content type and the file signature; a .png filename proves nothing.
  • Reject or sanitize active SVG content if your service will rehost it.

Key features for a dependable icon service

Source transparency

Return the selected source URL, final URL, detected media type, and update metadata. That lets clients explain why an icon was chosen and makes cache invalidation possible.

Conversion without replacing the original

Keep the downloaded source intact, then create delivery copies for each consumer. Use ICO when a multi-size raster container is expected, PNG for a single raster image, and SVG for scalable output.

Stable caching

Key cache entries by the normalized site URL and source icon URL. Reuse an unchanged asset, but publish a new versioned URL when the bytes change so clients do not keep displaying the old logo.

Pro tips for reliable lookups

  • Retain every candidate and the winning source; debugging becomes much easier.
  • Do not infer an icon from the domain name alone.
  • Fetch the final asset once, then serve a controlled copy if you need consistent formats and origin policy.
  • Use ETag or Last-Modified values where available to avoid unnecessary transfers.
  • Check the returned URL in a fresh tab; an empty response can still have a successful status code.

Conclusion

A reliable favicon API resolves declared resources, validates the returned bytes, and provides something stable enough to cache. Use Mzu favicondl for the interactive lookup and conversion step, then put those rules behind your own endpoint when the workflow needs automation.
